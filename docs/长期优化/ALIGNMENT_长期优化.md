# ALIGNMENT - 缺陷管理助手长期优化

## 项目上下文分析

### 现有项目结构

#### 技术栈
- **后端**：Node.js + TypeScript + Express + Prisma + MySQL
- **前端**：React + TypeScript + Ant Design + Vite
- **LLM**：DeepSeek API

#### 核心模块
1. **IntelligentQAService**：智能问答服务主入口
   - 处理用户请求
   - 意图识别和置信度判断
   - 错误处理和友好提示

2. **SkillManager**：技能管理器
   - 管理6个核心技能：DefectListSkill, DefectAnalysisSkill, TodoListSkill, NotificationSkill, DocumentGeneratorSkill, DataExportSkill
   - 支持技能注册、执行和验证

3. **IntentRecognizer**：意图识别器
   - 规则匹配（基于关键词和正则表达式）
   - LLM识别（DeepSeek API）
   - 多模型融合策略
   - 上下文增强

4. **LLMIntentParser**：LLM意图解析器
   - 调用DeepSeek API进行意图识别
   - 实体提取
   - 置信度评估

5. **ContextManager**：上下文管理器
   - 维护用户对话历史
   - 上下文增强
   - 上下文过期管理

6. **CacheManager**：缓存管理器
   - 意图缓存、实体缓存、数据缓存
   - LRU淘汰策略
   - 缓存统计

7. **FeedbackLearner**：反馈学习器
   - 收集用户反馈
   - 学习同义词和模式
   - 生成学习报告

#### 数据库模型
- `system_configs`：系统配置表
- `system_metrics`：系统监控指标表
- 其他业务表：projects, directories, test_cases, modules, scenarios等

### 现有代码模式

1. **单例模式**：所有服务类都使用单例模式导出
2. **类型定义**：使用TypeScript接口定义清晰的类型
3. **日志记录**：使用winston进行统一的日志记录
4. **错误处理**：统一的错误处理和友好提示
5. **配置管理**：支持环境变量和数据库配置

## 需求理解

### 对现有项目的理解

#### 1. 插件架构需求分析
**现状**：
- SkillManager已经实现了技能注册和执行
- 技能是硬编码的，在初始化时注册
- 没有动态加载机制

**需求理解**：
- 需要将现有的Skill接口标准化为插件接口
- 支持从外部目录或数据库加载插件
- 插件应该能够定义新的意图和技能
- 插件应该有自己的配置和生命周期

**技术约束**：
- 使用TypeScript的动态导入（import()）
- 插件需要遵循统一的接口规范
- 插件需要能够访问现有的服务（如数据库、日志等）

#### 2. 自动学习系统需求分析
**现状**：
- FeedbackLearner已经实现了基本的反馈收集
- 有学习数据存储（learning_data.json）
- 有简单的同义词学习和模式改进

**需求理解**：
- 需要增强FeedbackLearner的功能
- 实现更智能的学习算法
- 学习结果应该能够自动应用到IntentRecognizer
- 需要定期评估学习效果

**技术约束**：
- 学习算法不能过于复杂，避免过度设计
- 学习数据需要持久化到数据库
- 学习过程不应该影响系统性能

#### 3. 智能推荐系统需求分析
**现状**：
- ContextManager维护了用户对话历史
- 没有用户行为分析
- 没有推荐功能

**需求理解**：
- 需要分析用户查询模式
- 基于历史查询推荐相关功能
- 推荐应该在用户界面中展示
- 推荐结果需要个性化

**技术约束**：
- 推荐算法应该简单有效
- 需要存储用户行为数据
- 推荐结果应该实时更新

#### 4. 全面监控系统需求分析
**现状**：
- CacheManager有缓存统计
- ContextManager有上下文统计
- FeedbackLearner有学习报告
- 数据库中有system_metrics表

**需求理解**：
- 需要统一收集所有模块的监控数据
- 监控数据应该存储到数据库
- 需要开发监控仪表盘
- 监控指标应该包括性能、准确率、使用情况等

**技术约束**：
- 监控数据收集不应该影响系统性能
- 监控仪表盘应该使用现有的前端技术栈
- 监控数据需要定期清理

## 疑问澄清

### 关键决策点

#### 1. 插件架构相关
**Q1.1**：插件应该如何存储和加载？
- 选项A：从文件系统动态加载（推荐）
- 选项B：从数据库加载配置，代码在文件系统
- 选项C：完全从数据库加载（包括代码）

**决策**：选项A
- 理由：
  - 代码在文件系统便于开发和调试
  - 插件配置可以存储在数据库或配置文件
  - 动态加载可以使用Node.js的import()实现

**Q1.2**：插件是否需要沙箱隔离？
- 选项A：需要（安全性更高，但复杂度更高）
- 选项B：不需要（简单，但安全性较低）

**决策**：选项B
- 理由：
  - 系统是内部使用，信任插件开发者
  - 沙箱隔离会增加复杂度和性能开销
  - 可以通过代码审查保证插件安全性

**Q1.3**：插件是否需要版本管理？
- 选项A：需要（可以支持多版本共存）
- 选项B：不需要（简单，但灵活性较低）

**决策**：选项A
- 理由：
  - 支持插件升级和回滚
  - 可以兼容旧版本插件
  - 便于问题排查

#### 2. 自动学习系统相关
**Q2.1**：学习数据应该如何存储？
- 选项A：继续使用JSON文件（简单，但不利于查询）
- 选项B：存储到数据库（推荐）
- 选项C：混合存储（热数据在内存，冷数据在数据库）

**决策**：选项B
- 理由：
  - 便于查询和分析
  - 支持大规模数据存储
  - 与现有系统架构一致

**Q2.2**：学习算法应该多智能？
- 选项A：简单的规则学习（推荐）
- 选项B：机器学习算法（复杂，但效果可能更好）
- 选项C：混合方案

**决策**：选项A
- 理由：
  - 现有系统已经使用LLM，不需要复杂的ML算法
  - 规则学习简单可控
  - 避免过度设计

**Q2.3**：学习结果应该如何应用？
- 选项A：自动应用（实时更新）
- 选项B：人工审核后应用（推荐）
- 选项C：定期批量应用

**决策**：选项B
- 理由：
  - 避免错误的学习结果影响系统
  - 人工审核可以保证质量
  - 可以逐步验证学习效果

#### 3. 智能推荐系统相关
**Q3.1**：推荐算法应该使用什么策略？
- 选项A：基于内容的推荐（推荐相似查询）
- 选项B：协同过滤（基于用户行为）
- 选项C：混合策略（推荐）

**决策**：选项C
- 理由：
  - 结合两者的优点
  - 可以根据实际情况调整权重
  - 提供更准确的推荐

**Q3.2**：推荐结果应该如何展示？
- 选项A：在聊天界面中展示推荐问题
- 选项B：在侧边栏展示推荐功能
- 选项C：两者结合（推荐）

**决策**：选项C
- 理由：
  - 聊天界面中的推荐更直观
  - 侧边栏可以展示更多推荐
  - 提供更好的用户体验

**Q3.3**：推荐是否需要个性化？
- 选项A：需要（基于用户历史）
- 选项B：不需要（全局推荐）

**决策**：选项A
- 理由：
  - 个性化推荐更准确
  - 提升用户体验
  - 现有系统已经有用户上下文

#### 4. 全面监控系统相关
**Q4.1**：监控数据应该多久收集一次？
- 选项A：实时收集（每次请求）
- 选项B：定期收集（如每分钟）
- 选项C：混合策略（关键指标实时，其他定期）

**决策**：选项C
- 理由：
  - 关键指标（如错误率）需要实时
  - 其他指标（如缓存命中率）可以定期
  - 平衡性能和实时性

**Q4.2**：监控数据应该保留多久？
- 选项A：永久保留
- 选项B：保留一定时间（如30天）
- 选项C：根据重要性分级保留

**决策**：选项B
- 理由：
  - 避免数据量过大
  - 30天足够分析趋势
  - 可以定期清理

**Q4.3**：监控仪表盘应该包含哪些功能？
- 选项A：只展示数据
- 选项B：展示数据+告警
- 选项C：展示数据+告警+分析（推荐）

**决策**：选项C
- 理由：
  - 提供全面的监控能力
  - 帮助快速定位问题
  - 支持趋势分析
