# AI智能体场景分析：测试用例自动生成

## 一、场景价值判断

### 1.1 场景描述

在软件测试领域，测试用例设计是保障产品质量的核心环节。当前场景是：**基于产品需求文档，自动生成结构化、可执行的测试用例**。

本场景来源于实际的测试管理平台（AITestCraft），平台通过AI智能体将传统的"人工阅读需求→人工提炼测试点→人工编写测试用例"流程，转变为"上传需求→AI分析→自动生成测试点→AI生成测试用例→人工确认"的智能化流程。

### 1.2 为什么适合用AI智能体解决

#### ① 当前完成方式与效率瓶颈

**当前人工流程：**
1. 测试工程师阅读PRD需求文档（平均30-100页）
2. 人工提炼功能点、边界条件、异常场景
3. 根据测试设计方法（等价类、边界值、场景法等）设计测试点
4. 将测试点转化为标准格式的测试用例（包含步骤、预期结果、前置条件等）
5. 评审、修改、补充遗漏场景

**效率瓶颈与质量痛点：**
- **耗时严重**：一个中等复杂度功能模块的测试用例设计需要2-4人天
- **遗漏率高**：人工分析容易遗漏边界条件、异常场景（平均遗漏率15-25%）
- **质量不稳定**：依赖测试工程师经验，新手与专家产出质量差异大
- **重复劳动**：80%的测试用例属于常规场景，但需重复编写
- **知识难沉淀**：测试设计方法的应用依赖个人能力，难以标准化

#### ② AI介入后的价值

**输入：**
- 产品需求文档（支持PDF、Word、Markdown、TXT格式）
- 用户补充的场景描述或特定关注点
- 系统/模块/场景的结构化信息

**输出：**
- 结构化测试点列表（含设计方法标注）
- 完整测试用例（含编号、标题、前置条件、测试步骤、预期结果、优先级）
- 可导出为Excel的标准格式

**价值对象：**
- **测试工程师**：减少80%的基础用例编写时间，聚焦复杂场景和探索性测试
- **测试负责人**：提升团队产出标准化程度，降低对高级测试的依赖
- **研发团队**：加速测试准入，缩短交付周期
- **项目经理**：获得可量化的测试覆盖度评估

#### ③ 预计效率提升与质量改善

| 指标 | 人工方式 | AI辅助方式 | 提升幅度 |
|------|---------|-----------|---------|
| 测试点生成时间 | 4-8小时 | 5-10分钟 | **效率提升96%** |
| 测试用例编写时间 | 8-16小时 | 10-20分钟 | **效率提升98%** |
| 边界条件覆盖率 | 60-70% | 85-95% | **提升30%** |
| 异常场景覆盖率 | 40-50% | 75-85% | **提升60%** |
| 用例标准化程度 | 60% | 95% | **提升58%** |

**质量改善：**
- 消除因人为疲劳导致的遗漏
- 统一测试设计方法的应用标准
- 实现测试知识的标准化沉淀与复用

### 2.2 详细流程设计

#### ① 触发条件

| 触发类型 | 说明 | 触发者 |
|---------|------|--------|
| **主动触发** | 测试工程师在平台选择系统→模块→场景，输入/上传需求后点击"生成测试点" | 测试工程师 |
| **批量触发** | 基于已选中的测试点列表，点击"生成测试用例" | 测试工程师 |
| **定时触发** | 与CI/CD集成，代码合并后自动触发对应模块的测试用例生成（扩展） | 系统 |

**触发前置条件：**
- 已配置LLM Provider（DeepSeek/Volcano等）及API密钥
- 已选择测试对象（系统-模块-场景三级结构）
- 已提供需求输入（文本或文档）

#### ② 输入信息的来源与格式要求

**输入来源：**

| 输入类型 | 格式要求 | 示例 |
|---------|---------|------|
| 需求文本 | 纯文本，长度100-10000字 | "用户登录功能：支持手机号+密码登录，密码长度8-16位..." |
| 需求文档 | PDF/DOCX/MD/TXT，支持章节选择 | 上传PRD文档，选择"登录功能"章节 |
| 结构化信息 | JSON格式，包含系统/模块/场景 | `{system: "电商平台", module: "用户中心", scenario: "登录"}` |
| 历史用例 | 已有测试用例库，用于风格对齐 | 历史登录功能用例10条 |

**输入预处理：**
1. **文档解析**：提取文本内容，识别章节结构
2. **内容清洗**：去除页眉页脚、页码、格式标记
3. **语义分段**：按功能点、规则、流程进行段落切分
4. **关键信息提取**：识别输入条件、业务规则、异常场景

#### ④ 异常路径处理

| 异常场景 | 处理方式 | 用户感知 |
|---------|---------|---------|
| LLM API超时 | 重试3次，间隔2秒；仍失败则切换备用Provider | 显示"正在尝试其他模型..." |
| LLM返回格式错误 | 使用正则提取JSON；失败则使用文本解析 | 无感知，后台自动处理 |
| 生成测试点过少(<3条) | 自动补充提示词，要求LLM扩展场景 | 显示"正在补充测试场景..." |
| 生成测试点过多(>50条) | 按功能模块分批处理，每批10-15条 | 显示进度条，分批加载 |
| 文档解析失败 | 回退到原始文本，跳过章节提取 | 提示"已使用原始文本模式" |
| 用户未选择任何测试点 | 禁用"生成用例"按钮，提示"请至少选择一个测试点" | 按钮置灰+Tooltip提示 |
| 用例编号重复 | 后端重新计算编号，基于当前总数 | 无感知，自动修正 |

#### ⑤ 最终输出物与接收对象

**输出物1：测试点列表**
- 格式：JSON数组，前端以表格展示
- 内容：序号、测试点描述、设计方法（Tag展示）
- 接收对象：测试工程师（确认/编辑/选择）

**输出物2：测试用例列表**
- 格式：JSON数组，支持导出Excel
- 内容：用例编号、标题、前置条件、测试步骤（有序列表）、预期结果（有序列表）、优先级
- 接收对象：测试工程师（保存到用例库）

**输出物3：导出文件**
- 格式：Excel (.xlsx)
- 内容：标准化测试用例表格，含所有字段
- 接收对象：测试团队（导入测试管理系统）

### 3.2 核心LLM节点提示词框架

#### 提示词1：测试点生成

```markdown
## 角色
你是一名经验丰富的软件测试分析工程师，擅长从自然语言需求中提取出清晰、可验证的功能测试点。

## 任务
根据用户输入的测试对象及需求描述，转化为一组测试点清单。

## 设计方法选择指南

1. **等价类划分** - 用于输入条件可以划分为若干等价类的情况
2. **边界值分析** - 用于测试边界条件的情况（如长度刚好为边界值）
3. **场景法** - 用于测试业务流程或用户操作场景
4. **错误推测法** - 用于测试异常情况或错误处理（如连续错误输入）
5. **判定表驱动法** - 用于多条件组合的情况
6. **状态迁移法** - 用于测试状态变化（如账户状态变化）

## 输出要求
1. 语句简洁，覆盖明确的功能或行为
2. 包含主流程、边界条件、异常输入等常见测试场景
3. 为每个测试点指定最合适的设计方法
4. 输出格式为 JSON 数组

## 输入
系统: {system}
模块: {module}
场景: {scenario}
需求描述: {requirement}

## 输出格式
[
  {
    "content": "测试点内容描述",
    "designMethod": "设计方法名称"
  }
]
```

#### 提示词2：测试用例生成

```markdown
## 角色
你是一名资深的软件测试工程师，负责根据产品需求和测试点设计高质量的测试用例。

## 任务
根据测试点编写结构化、规范化的测试用例。

## 输出要求
1. 每条测试用例都准确覆盖指定的测试点
2. 所有测试用例均符合格式要求
3. 测试用例应覆盖所有测试点

- number: 测试用例编号

## 输入
测试点列表: {test_points}
上下文信息: {context_info}

## 输出格式
[
  {
    "number": "Test0001",
    "title": "...",
    "precondition": "...",
    "steps": ["步骤1", "步骤2", "步骤3"],
    "expected_results": ["结果1", "结果2", "结果3"],

]
```

### 3.3 最终交付物

**智能体交付物形式：**

1. **Web应用界面**
   - 三步向导式流程：输入需求 → 选择测试点 → 查看测试用例
   - 测试点表格展示（含设计方法Tag）
   - 测试用例表格展示（支持悬浮查看完整内容）
   - 详情弹窗查看完整用例信息

2. **API接口**
   - `POST /api/generate-points` - 生成测试点
   - `POST /api/generate-cases` - 生成测试用例
   - `POST /api/export-excel` - 导出Excel

3. **标准化输出文件**
   - Excel格式测试用例文档

## 四、技术实现亮点

### 4.1 智能设计方法识别

不依赖AI生成设计方法（AI经常全部输出"等价类划分"），而是采用**后端规则引擎**自动识别：

```typescript
// 基于关键词的优先级匹配
const rules = [
  { method: '边界值分析', keywords: ['小于', '大于', '等于', '长度'] },
  { method: '错误推测法', keywords: ['连续', '多次', '锁定'] },
  { method: '状态迁移法', keywords: ['状态', '锁定', '激活'] },
  // ...
];
```

**优势：**
- 识别准确率 > 90%
- 响应时间 < 1ms
- 不依赖LLM，零成本

### 4.2 多Provider适配

支持DeepSeek、Volcano Engine等多个LLM Provider，可动态切换：

```typescript
interface LLMProvider {
  generatePoints(params: GeneratePointsParams): Promise<TestPoint[]>;
  generateCases(params: GenerateCasesParams): Promise<TestCase[]>;
}
```

### 4.3 异步任务处理

采用SSE（Server-Sent Events）+ HTTP轮询双模式，确保大模型响应的实时性：

```
用户点击生成 → 创建异步任务 → SSE推送进度 → LLM处理 → 返回结果
                └─► 超时 fallback 到 HTTP轮询
```
